## State and database

Shielded notes, commitments, roots, and nullifiers are handled by the client and protocol contracts. The app database must not receive note secrets or become the source of truth for pool state. The pool indexer and association set are rebuilt from confirmed chain events and reject reorged snapshots. There is no Shield-specific SQL migration. The server relayer requires the existing shared `rate_limits` table from migration `0002_rate_limits.sql` and fails closed if the database-backed limiter is unavailable. The unrelated ZK creator-binding/revocation migration `0008_zk_creator_binding_and_revoke.sql` is a separate feature and was previously applied to the configured database.

## Before any testnet deployment

1. Review the deterministic public test dataset and publish its immutable content-addressed CID. Compute the LeanIMT root from that exact dataset and verify it against the circuit's Poseidon/LeanIMT implementation.
2. The testnet setup supports one funded operator wallet for deployment, ASP root updates, relayed withdrawals, and the guardian pause. The optional role-specific keys/guardian address in `.env.local` can override that default. A shared wallet can stop deposits and update ASP roots; it cannot withdraw or move pool funds. This shared-role setup is for testnet rehearsal only.
3. Confirm the configured or default RPC reports chain ID 46630. Entrypoint owner authority is renounced after pool registration; the operator retains the ASP postman role.
4. Compile with `npm run compile:privacy-pools`. Review the generated verifier interfaces and artifact checksums against `public/shield-artifacts/v1.2.1/ARTIFACTS.md`.
5. Deploy only with an explicit acknowledgment and the reviewed dataset parameters:

   ```powershell
   npm run deploy:privacy-pools:testnet:small
   npm run shield:publish-asp
   ```

   Set `SHIELD_DEPLOYMENT_MANIFEST=robinhood-testnet-privacy-pools-v1.2.1-0.001eth.json`. Fill only `SHIELD_DEPLOYER_PRIVATE_KEY` for the single-wallet setup; optional postman, relayer, and guardian overrides can stay empty. Existing `SHIELD_ASP_ROOT` and `SHIELD_ASP_CID` bootstrap the new Entrypoint; the ASP publish command then pins a pool-specific dataset and updates the new root. The deploy command loads `.env.local`, checks chain ID and reusable contract bytecode, registers a 0.001 ETH minimum with zero vetting and relay fees, then renounces the new Entrypoint owner role. Never paste wallet keys into the browser or commit them.

6. The runtime reads the selected manifest and verifies the 0.001 ETH onchain denomination and 10 ETH cap. By default, the deployer key also signs relayed withdrawals; optional relayer key/address settings can override it. Verify deployed bytecode and role/configuration values from a second RPC/client. Exercise deposit, proof generation, withdrawal, ragequit, cap, guardian pause, and recovery with test accounts before changing any application flag.

## Operational boundaries

- Keep `SHIELD_ENABLED`, `SHIELD_DEPOSIT_ENABLED`, and `SHIELD_WITHDRAW_ENABLED` false until the rehearsal checklist is complete. Deploying contracts does not activate the feature.
- No mainnet deployment, production policy, legal/compliance claim, or privacy guarantee is implied by a testnet rehearsal.
- The old `scripts/deploy-shielded.mjs` entry point now exits because its pool accepts arbitrary mock proofs.
- Run `npm run test:shield:evm` with Foundry 1.8.3 installed to execute the pinned `PrivacyPoolSimple` source in a local EVM. The suite checks denomination/cap, pause and guardian behavior, withdrawal accounting, replay, recipient-context binding, invalid verifier results, and 256 fuzzed deposit/withdraw sequences. Its verifier and Entrypoint collaborators are test-only; the suite does not prove Groth16 soundness.
- Mainnet runtime selection uses `SHIELD_CHAIN_ID=4663`, `SHIELD_MAINNET_RPC_URL`, and `SHIELD_MAINNET_DEPLOYMENT_MANIFEST`; the defaults never reuse the testnet manifest. The testnet remains `46630` with its existing settings. `SHIELD_MAINNET_VERIFIER_READY=true` records only the internal artifact compatibility review in `Shield-Mainnet-Technical-Review.md`; normal Shield activation flags stay false until deployment and rehearsal are complete.
- `SHIELD_OPERATOR_ADDRESS` and `SHIELD_MAINNET_GUARDIAN_ADDRESS` use the same public wallet address. Mainnet deployer, postman, and relayer keys use separate env names and must derive that same one-wallet address. The current ignored `.env.local` values were copied from the matching testnet key; `SHIELD_MAINNET_BROADCAST_ENABLED` remains false. Mainnet association root/CID use `SHIELD_MAINNET_ASP_ROOT` and `SHIELD_MAINNET_ASP_CID`, isolated from testnet values.
- `npm run shield:check-mainnet-readonly` checks the public RPC and reports missing deployment state without writing. `npm run shield:publish-mainnet-genesis-asp` publishes a public single-sentinel genesis dataset to IPFS (no chain transaction). `npm run shield:prepare-mainnet` validates the RPC, wallet balance, and published ASP dataset without signing. `npm run deploy:privacy-pools:mainnet` recompiles with Solidity 0.8.28, validates pinned deployment artifact hashes, and builds a mainnet transaction plan; it is dry-run by default. The separate `deploy:privacy-pools:mainnet:broadcast` command requires `SHIELD_MAINNET_BROADCAST_ENABLED=true`, matching one-wallet keys, the open verifier review gate, and sufficient balance; it leaves the pool deposit-paused and does not activate it. Before writing the manifest, it verifies verifier/Entrypoint addresses, pool denomination/cap, native-asset registration and fees, scope registration, ASP root/CID, pause state, and roles. Deployed Poseidon library addresses are included in the manifest. A separate guardian transaction is required to open deposits after service checks.
- The testnet deployment helper remains testnet-only. There is no mainnet manifest or pool and no mainnet transaction was sent. Local EVM invariants exercise pool bytecode with test-only verifier collaborators. Mobile, second-device, and legal checks were waived by the owner.
